A workflow starts from an explicit run request or a project cron. The `on` field declares whether a workflow accepts manual runs. Cron schedules are separate project files, so one workflow can have multiple schedules with different inputs.

## Manual runs

A workflow must declare `manual: true` to accept an explicit run:

```yaml
name: release-manager
version: "1.0.0"
on:
  manual: true
jobs:
  release:
    runsOn: local
    steps:
      - name: Publish release
        uses: builtin:shell
        with:
          command: echo "release requested"
```

Run it from the CLI and pass JSON inputs with `--input`:

```bash
kb workflow run --workflow-id=release-manager --input='{"version":"1.0.0"}'
```

The run record identifies `trigger.type: manual`. Use `kb workflow runs status <runId>` and `kb workflow runs logs <runId>` to inspect the result.

## Cron schedules

Create `.kb/crons/nightly.yml` to schedule an existing workflow:

```yaml
schedule: "0 3 * * *"
timezone: "Europe/London"
workflow: release-manager
input:
  version: stable
enabled: true
```

Use `kb workflow crons list` to inspect schedules and `kb workflow crons disable nightly` or `kb workflow crons enable nightly` to change a user cron. A project cron can also target a registered job handler. Plugin manifest crons appear as read-only entries.

The run's `trigger.type` is `schedule`, and `metadata.cronId` identifies the schedule.

## Validation

The `on` object must contain `manual: true`; an empty object or an unsupported trigger field fails workflow validation. The workflow schema does not declare Git push or webhook delivery triggers. Plugin webhook endpoints are a separate plugin surface.
