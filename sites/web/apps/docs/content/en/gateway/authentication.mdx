KB Labs installs have two access modes. **Local** mode binds to loopback and signs requests in as `local-admin`; it does not show a login screen. **Secured** mode requires a user session for Studio, Gateway APIs, and project services. Choose secured access when teammates or remote clients need accounts.

Implementation: `services/gateway/app/src/auth/user-routes.ts`, `services/gateway/app/src/auth/user-auth-middleware.ts`, and `services/gateway/auth/src/api-tokens-store.ts`.

## Sign in and inspect permissions

For browser clients, Studio uses `/login`. For scripts, log in with the CLI and inspect the current identity:

```bash
kb auth login --gateway-url https://gateway.example.com --email admin@example.com
kb auth status
```

When run in a terminal, the CLI prompts for the password without displaying it. For automation, pass it through standard input instead of an argument:

```bash
kb auth login --gateway-url https://gateway.example.com --email admin@example.com --password-stdin < ./admin-password.txt
```

The CLI stores the human session at `~/.kb/session.json`; `kb auth status --json` reports its resolved path as `data.session.path`. The file contains a refresh token and is readable only by its owner. The CLI refreshes the short-lived access token when needed. `kb auth logout` revokes the server refresh family before deleting the local session.

The authenticated user can inspect their profile and effective permissions through `GET /auth/me` and `GET /auth/permissions`. Requests use the session Bearer token from CLI login, or the Studio session cookies.

## Invite a teammate

An administrator creates an invite and shares the returned activation link directly. There is no email delivery in this flow. The role must be `member` or `admin`; a member cannot create invites or manage accounts.

```http
POST /auth/invites
Authorization: Bearer <admin-access-token>
Content-Type: application/json

{"email":"dev@example.com","role":"member"}
```

The response contains an `activationUrl` under `/activate/<token>`, which is the Studio route. The invitee opens it, chooses a password, then signs in. Administrators can view pending invites in Studio at `/admin/invites`.

## Reset a user's password

An administrator can create a one-time reset link in Studio's Users page or from the CLI:

```bash
kb auth reset-link --user-id usr_123
```

Replace `usr_123` with the user's ID shown on the Users page. The JSON result contains `resetUrl` and `expiresAt`. Share the link out of band. It expires after 24 hours, works once, and revokes all existing sessions when redeemed. KB Labs does not email the link.

If no administrator can sign in, stop the host and use operator recovery. Supply the new password through standard input:

```bash
kb-create stop
kb-create doctor --recover --email admin@example.com --tenant kb-cloud --password-stdin --yes
kb-create start
```

The tenant must match the configured bootstrap administrator tenant. To have the doctor generate a replacement password, use `--generate` instead of `--password-stdin`; keep the printed value private.

## Personal API tokens for agents and CI

Each user can create a personal API token from Studio at `/account/tokens` or the CLI. A token inherits the owner's current role permissions, is scoped to that user, and expires after 90 days. The plaintext is shown only once. Listing and revoking tokens are owner-scoped.

```bash
kb auth tokens --name "nightly CI"
kb auth tokens
kb auth tokens --revoke tok_abc123
```

Send a token as an `Authorization: Bearer` header:

```bash
curl https://gateway.example.com/auth/me \
  -H "Authorization: Bearer $KB_API_TOKEN"
```

Store the secret in CI's secret manager. Do not commit it to source control. Revoke it with its token ID when the agent is removed or the secret is exposed.

## Roles

| Role | Access |
|---|---|
| `admin` | Use projects, plugins, and workflows; manage users and invites; change platform settings; create reset links. |
| `member` | Use projects, plugins, and workflows; manage their own password, sessions, and API tokens. |

Studio checks the permission list returned by the Gateway and hides actions the current user cannot perform. The Gateway enforces the same policy on each protected route.
