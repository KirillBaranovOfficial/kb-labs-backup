## Goal

As a KB Labs user or automation author, I can tell whether an operation succeeded, understand and act on a failure, and consume the same machine-readable result across commands, HTTP, MCP, and Studio. Unexpected failures can be correlated with platform logs without exposing stack traces in user-facing output.

## Prerequisites

- [ ] Local and secured platform fixtures with registries of all CLI commands, HTTP routes, MCP tools, and Studio error boundaries.
- [ ] Registry-provided valid, invalid-input, typed-failure, and unexpected-failure fixtures; an unexpected failure can be correlated with structured logs.

## Steps

| # | Action | Expected |
|---|---|---|
| S-203.1 | In machine mode, invoke every registered TS and Go CLI command, every live Gateway and REST HTTP route, and every MCP tool through its registry using valid fixture input | Each successful result uses `{ "ok": true, "data": ... }` with optional `meta`. Command, route, or tool payloads (including doctor/status objects) are inside `data`. Diagnostic/report commands succeed with exit 0 and include `data.status` as `healthy`, `degraded`, or `unhealthy` alongside their report, even when findings identify problems. JSON health and readiness routes (`/health`, `/health/adapters`, `/health/auth`, `/api/v1/health`, `/ready`, and project-routed health) follow the same envelope; their consumers validate the envelope before reading the payload. Gateway `/ready` preserves the readiness payload fields `schema`, `ts`, `ready`, `status`, `reason`, and `components` inside `data`; project routing reports `components.projectRuntimes.ready` and its active/limit status. When project routing is enabled, Gateway `/health` includes `data.projectRuntimes` with `limit`, `active`, and each runtime's `projectId`, `state`, `lastUsedAt`, `inflight`, `restarts`, and optional `keptRunningSchedules`; it contains no process IDs, addresses, paths, or failure causes. This applies to every route discovered from each running Fastify route registry, including routes added after the coverage test was written. For every registered system and plugin CLI command, stdout parses as exactly one JSON envelope and contains no logs, warnings, progress, or other diagnostics; human progress output is written to stderr. System commands return typed result data or throw catalogued errors, and the shared CLI serializer emits the only JSON envelope; plugin handlers cannot print JSON through `ctx.ui.json` or errors through `ctx.ui.error`; typed UI access omits these methods, and a runtime call from JavaScript or an out-of-tree plugin fails with catalogued `KB_PLUGIN_CONTRACT_VIOLATION` and a hint to return data or a typed failure. The shared CLI dispatch serializes the returned command result once. HTTP retains its status semantics; MCP returns the envelope in `structuredContent` and keeps successful MCP signaling. Go tool CLIs apply this contract at their shared Cobra command boundary for every registered `kb-dev`, `kb-devkit`, and `kb-create` command, including install, update, rollback, and doctor; no handler writes directly to terminal output. |
| S-203.2 | Invoke every registered CLI command and every live Gateway and REST HTTP route with invalid input and a typed failure; invoke an unknown CLI command; invoke every MCP tool with invalid input, an undeclared argument for tools without declared inputs, and the built-in MCP diagnostics tool without authorization in secured mode | Each failure uses `{ "ok": false, "error": ... }`, where `error` is the platform `ErrorEnvelope` with a stable catalogued `KB_*` code, message, actionable hint, and correlation ID where applicable. Structured gate findings are carried only in `error.diagnostics`, an array of `{code,message,severity,path?,line?,hint?}` records; `details` remains a flat string map of identifiers and never contains serialized JSON. The plugin-contracts `CommandFailure` is the sole command failure type and requires a catalogued code, message, and actionable hint; the shared CLI renderer uses those fields, diagnostics, and any string-map details in both JSON and human modes. Catalogued execution errors retain their code, message, hint, details, diagnostics, and correlation ID; only uncatalogued failures become `KB_RUNTIME_UNEXPECTED`, whose real cause is available in structured logs with the same correlation ID. An unknown CLI command uses the shared envelope with a catalogued `KB_*` code and a hint to check the command or list available commands, never `CMD_NOT_FOUND` or a raw error shape. Gateway and REST preserve the route's appropriate non-2xx HTTP status; deliberate HTTP failures, request validation failures, and secured 401/403 responses use the same envelope. Every code emitted by a Go tool exists in the platform error catalog; a missing code is rendered as `KB_RUNTIME_UNEXPECTED`. CLI exits 2 for invalid usage/input and 1 for other operation failures; MCP sets `isError: true`, puts the envelope in `structuredContent`, and includes its readable message and hint in text content. A secured request without a token returns HTTP 401 with the same error envelope. Go tool CLIs, including kb-create, use exit 2 only for invalid usage/input and exit 1 for every other failure. Invalid input and typed operation failures from kb-create install, update, rollback, and doctor include a catalogued code, actionable hint, and correlation ID in both human and JSON modes. No surface returns a raw error or stack. |
| S-203.3 | Cause an unexpected failure in every registered CLI command, every live Gateway and REST HTTP route, and every MCP tool | Each failure is `KB_RUNTIME_UNEXPECTED` and includes a correlation ID. The matching structured log entry contains the stack and same correlation ID. Gateway and REST response bodies, human output, machine responses, MCP content, and Studio UI contain no cause or stack; MCP retains `isError: true` and shows the correlation ID, while surfaces with actions offer copy diagnostics. Go tool CLIs, including kb-create, assign a correlation ID to every failure at their shared boundary and log unexpected-error stacks as structured records carrying that same ID. |
| S-203.4 | Run every registered CLI command in human mode against the valid and failure fixtures | One shared renderer shows the error code, plain-language message, why it failed when known, and the exact next step as `Hint: <hint>`. It reports success only after the handler returns normally; a void/undefined handler return means successful command execution and serializes as `data: null` in machine mode. Command postconditions remain the command's responsibility and are checked by its product case. |
| S-203.5 | Cause route, widget, and plugin-page failures by enumerating the live Studio router, widget, and federation registries; decode shared valid and invalid API-result fixtures; visit empty, loading, failed, unconfigured, and unavailable states | Every registered boundary presents a safe failure with a stable `KB_*` code, plain-language message, actionable hint, and correlation ID. Typed failures retain their envelope fields; unexpected failures use `KB_RUNTIME_UNEXPECTED` and a generated correlation ID. Copy diagnostics contains the code and correlation ID, never a raw error or stack. The API client decodes valid shared envelopes and turns invalid responses into a typed safe error using the platform's canonical UX-result validator through a browser-safe package subpath. Raw errors and stacks do not appear in the UI or ordinary `console.error`/`console.warn` calls; unexpected stack details are retained only by structured diagnostics. Empty, loading, failed, unconfigured, and unavailable states are visibly and accessibly distinguishable, with a recovery action where one exists. |
| S-203.6 | Run the automated registry coverage check for all registered CLI commands, every live Gateway and REST HTTP route, MCP tools, and Studio error boundaries | The check discovers entries from the live registries rather than a hand-maintained route or command list, applies valid, invalid/typed-failure, and unexpected-failure fixtures, and reports every registration as covered or identifies the missing result/error contract. For Gateway and REST, it boots production route registration with test doubles and walks Fastify's live route registry. Every JSON route has a declared schema from which the check builds valid and invalid request fixtures; a JSON route without a schema is a finding and fails the check. Every route that intentionally returns non-JSON (such as static assets, text responses, SSE, or WebSocket upgrades) declares `config.ux: 'raw'` on its route definition; the check reads that declaration and never infers an exemption. JSON health and readiness routes, including `/health`, use the same UX result envelope as every other JSON route. For each JSON route, the check validates a successful response, a typed or validation failure with its HTTP status and actionable hint, and an injected unexpected failure against `contracts/ux-result/`; unexpected failures are `KB_RUNTIME_UNEXPECTED` with a correlation ID and no response stack. Adding a route without boundary or fixture coverage makes the check fail. For MCP, every tool produced from the registry is exercised against the shared result schema and valid/failure fixtures. Go tool CLI coverage walks the live Cobra command trees for `kb-dev`, `kb-devkit`, and kb-create; for every leaf it invokes help and invalid input, then invokes a safe read-only command in every command group in machine mode and validates the single envelope against `contracts/ux-result/`. Adding a registration or leaf without the shared boundary or fixture coverage, or emitting an uncatalogued code, makes the check fail. |

## Contract reference

Machine results use the shared schema and fixtures in `contracts/ux-result/`. Every CLI and HTTP/MCP machine result is an envelope: success is `{ "ok": true, "data": <payload>, "meta"?: {...} }`; failure is `{ "ok": false, "error": <ErrorEnvelope> }`. The platform error type is defined in `core/platform/src/error-envelope`.
